Graph-driven frontend testing

Point it at your app. It walks every screen.

uiscout clicks every safe control, types into every field and follows every screen it can reach, then judges each step with deterministic checks. You get a map of the app and a list of real defects. No spec to write, no model, the same result on every run.

Get started Read the report
uiscout check --url http://localhost:5173/ --open
34 / 35navigation patterns observed on uigraph's gauntlet, with a five-line config
2 bugsfound and fixed in a real calendar app on the first run, with no spec
25 sfor an affected-only pull request run, against 42 s for the whole app
1 movea planted drag bug, found by an adapter and shrunk to a single action

Three kinds of check, one walk

Every step the walker takes is judged three ways. The first needs nothing from you. The other two grow with the project.

ORACLE A · ZERO SETUP

Is the app broken?

Generic checks that hold for every web app.

  • scriptuncaught exceptions, console.error
  • network5xx, unexpected 4xx, failed calls
  • dead-controla click that can't land
  • layoutoverlaps, clipped text
  • a11yserious axe rules
ORACLE B · YOUR RULES

Does it do the right thing?

Business rules in TypeScript, checked on every path. Product people write the sentences in intent files; the report shows which are covered.

  • alwaysan invariant in every state
  • when().then()an implication
  • eventually().within()a deadline, on the app's clock
ORACLE C · BASELINE

Is it different from yesterday?

An accepted run is committed as a lockfile. Every later run is compared to it, and git diff uiscout/ is the review.

  • errora control gone, renamed, or leading elsewhere
  • warninga control moved more than 16 px
  • infoa new control

Where it fits

Hand-written end-to-end tests check the paths someone thought of. Static graph tools read routes from code and stop at routers they don't support. uiscout watches what the running app actually does.

GUIDE · 01

Install and first run

You need Node 24 or later, pnpm 10, and a web app that is running and reachable from a browser: a dev server, vite preview or staging.

Install it as a dev dependency. Rules, adapters and the Vite plugin import uiscout/rules, uiscout/adapter and uiscout/vite, so this is the setup to choose for anything beyond a plain check.

pnpm add -D github:nguyentrinhquy1411/uiscout   # builds dist/ on install
pnpm exec playwright install chromium
pnpm exec uiscout check --url http://localhost:5173/ --open

Clone it once and call it by path. Nothing in the app changes.

git clone https://github.com/nguyentrinhquy1411/uiscout.git ~/dev/uiscout
cd ~/dev/uiscout && pnpm install && pnpm exec playwright install chromium
alias uiscout="node ~/dev/uiscout/src/cli.ts"     # add to ~/.zshrc

cd ~/dev/my-app && uiscout check --url http://localhost:5173/ --open

To use rules or adapters from a checkout, link it into the app: pnpm add -D link:../uiscout.

Run from the app's root directory: uiscout reads its config, rules and intent files from there. If the app calls paid services (AI, SMS, payments), block them from the very first run with --block "**/api/ai/**".

What you get

OutputWhere
Short reportThe terminal, and .uiscout/report.txt
Map of the app.uiscout/graph.html, opened by --open
Raw datagraph.json, findings.json, snapshots.json
A screenshot per screen.uiscout/screens/*.jpg
Pull request comment.uiscout/report.md

Add .uiscout/ to .gitignore. The command exits with 1 when it found errors.

GUIDE · 02

The check command and its report

Each screen opens in a fresh browser context (1280×800, animations off), four at a time. Buttons, links, tabs, menu items, checkboxes and switches are clicked; text fields get uiscout typed into them, then Enter. After every step uiscout waits until no request is in flight and the DOM has been still for 250 ms, fast-forwards the page clock by 5 s to catch delayed navigation, then runs the checks.

uiscout: 1 errors, 2 warnings · 11 nodes, 223 edges, 227 steps

Errors (1)
  script       console.error: Error: Base UI: MenuGroupContext is missing.
               at / → click /.button:account@nav · /calendar → click … · +5 more

Warnings (2)
  a11y         button-name: Buttons must have discernible text — #nameless
               at load /broken.html

Healed lookups (8)    found by similarity, not exact match
Flaky (1)             failed, then passed from a fresh context
Not walked: 2 destructive, 1 input, 39 repeat

Errors and warnings are counted by message: the same error on seven screens counts once. at load /x means on arriving at /x; /x → click Y means after clicking Y there.

Cutting noise

SymptomFix
Elements overlap by design (stacked events)--allow-overlap "[data-event-id]"
An expected 4xx (a session check)--allow-4xx "GET /api/me"
console.error from a library"ignoreConsole": ["text"]
Dates change the snapshots every day--now 2026-10-07T09:00:00+07:00

How long it takes

About 0.4–2 s per step. Screens run in parallel but the steps on one screen don't, so the total is close to the busiest screen. On a calendar app: depth 1 about 110 s (70 s with --no-a11y --fast-forward 0); depth 2, 31 screens and 431 steps, about 4 minutes.

GUIDE · 03

Configuration

Put uiscout.config.json in the app's root. Flags always override it.

{
  "url": "http://localhost:5173/",
  "depth": 2,
  "maxSteps": 600,
  "now": "2026-10-07T09:00:00+07:00",
  "seeds": ["/legacy", "/no-such-page", "/account"],
  "contexts": [
    { "name": "guest" },
    { "name": "member", "setup": [
      { "route": "/login" },
      { "fill": "Email", "text": "demo@example.com" },
      { "fill": "Password", "text": "demo-password" },
      { "click": "Log in" }
    ] }
  ],
  "block": ["**/api/ai/**"],
  "allow4xx": ["GET /api/me"],
  "allowOverlap": "[data-event-id]",
  "ignoreConsole": ["Download the React DevTools"],
  "network": "live"
}

Contexts

A context is a persona with setup steps that run after every page load, so apps that keep the session in memory work too. The graph records which contexts saw each screen and edge: the guest's /pricing → /login and the member's /pricing → /account both appear.

StepDoes
{ "route": "/login" }In-app navigation through the history API. Prefer it for single-page apps
{ "goto": "/login" }A full page load; in-memory state is lost
{ "fill": "Email", "text": "…" }Types into the field with that label or placeholder
{ "click": "Log in" }Clicks the button or link with that name
{ "press": "Enter" }Presses a key
{ "eval": "…" }Runs JavaScript in the page

Seed routes

Routes no link reaches (a 404 page, an old URL that redirects) are entered from the entry through the history API. A seed that redirects is kept as a route edge, such as /legacy → /pricing.

Use test accounts. The config is plain text and gets committed.

GUIDE · 04

The graph page and snapshots

Every run writes .uiscout/graph.html, one offline page with the whole app as it was walked.

uiscout check --open                          # open it when the run ends
uiscout graph --open                          # reopen the last run, no browser run
uiscout graph uiscout/app.graph.json --open   # the committed baseline
  • Columns are steps from the entry. Solid boxes are screens, dashed boxes are overlays (dialogs, menus), a red border means errors, and badges count errors and warnings.
  • Click a screen to open its panel: findings, snapshot, how to get there, every action from it with the API calls it made, and the ways in.
  • Snapshots show the screenshot with a box over each control (green button, purple link, orange field). Switch to screenshot or wireframe only; click for full size.

The text form of a snapshot is the same as in a baseline: role, name, landmark, position and size rounded to 4 px, and the test ID.

button "Save" @main 640,96 80x32
link "Docs" @nav 12,180 36x36 #shell.Rail.docs

Screenshots are on locally and off when CI is set. They show whatever the app shows, so pass --no-screenshots when the output is shared and the app displays personal data.

GUIDE · 05

Baselines

The generic checks catch "the app is broken". A baseline catches "the app is different from yesterday".

uiscout check --update                # accept the current state
git add uiscout/ && git commit -m "uiscout baseline"

uiscout check                         # later: compare with it
uiscout check --update && git diff uiscout/   # accept an intended change, review it
File in uiscout/Contents
app.graph.jsonEvery screen and edge, in a fixed order
snapshots/<screen>.txtOne line per control
paths.jsonHow each screen was reached, for affected runs
recordings.jsonAPI responses from --mode record
ChangeSeverityMessage
A control is goneerrorbutton "Load data" is gone
Role or name changederrorbutton "Count 0" became button "Counter 0"
An action leads elsewhereerrornow leads to /dialog.html, was /
Graph changed without --updateerrorapp.graph.json is out of date

Keep it stable

A baseline only helps when two runs of the same commit agree: fix the time with now, use the same data every run, block anything that varies, and take the baseline in the mode CI uses. Then run check twice; both must say Graph diff (no change). A calendar app at depth 2 (31 screens, 352 edges) reran with no change.

GUIDE · 06

Network modes

--modeBackendUse it for
liveRealLocal and first runs. Destructive controls are never clicked
recordRealWalks like live and keeps every API response, redacted
replayNoneAnswers from the recordings. Fast, stable, and walks destructive controls too
 
uiscout check --mode record --update   # once, against a test backend
uiscout check --mode replay --update   # the baseline, in the mode CI uses
uiscout check --mode replay            # every run after: no backend needed

Replay fails closed: every API call, beacon and form POST to any origin is answered from the recordings or stopped. A call with no recording gets status 599 and a warning telling you to re-record. Navigation to other sites gets a stand-in page.

Still open in replay: same-origin GET navigations reach the server. A server-rendered app with a GET /logout route still receives it.

Running in CI

WhenCommand
Every pull requestcheck --mode replay --affected origin/<base>

The API changedcheck --mode record --update, by hand
 
# .github/workflows/uiscout.yml (core steps; full file in examples/)
- uses: actions/checkout@v4
  with: { fetch-depth: 0 }               # history for --affected
- run: pnpm install --frozen-lockfile
- run: pnpm exec playwright install --with-deps chromium
- run: pnpm build --mode test && (pnpm preview --port 4173 &)
- run: pnpm exec uiscout check --url http://localhost:4173/ --mode replay --affected origin/${{ github.base_ref }}
- if: always()
  run: gh pr comment ${{ github.event.pull_request.number }} --edit-last --create-if-none --body-file .uiscout/report.md

The pull request gets one comment, updated on each push: the verdict, graph changes as a diff, the errors, intent coverage, usage-weighted coverage, and the full report folded. When a change is intended, run check --mode replay --update locally, review git diff uiscout/ and commit.

GUIDE · 08

Vite plugin and affected-only runs

Without the plugin, controls are known by fingerprint. With it, every interactive JSX element gets a steady ID and the file it comes from.

// vite.config.ts
import { uiscoutIds } from 'uiscout/vite'

export default defineConfig(({ mode }) => ({
  plugins: [mode === 'test' && uiscoutIds(), react()],
}))
<button data-scout-id="cart.CartSummary.submitOrder"
        data-scout-src="src/features/cart/CartSummary.tsx:48">Place order</button>

The ID is <module>.<Component>.<hint>, the hint taken from the handler, then the label, then the text, never from position, so relabelling a button keeps its identity. A data-testid wins.

With a baseline taken while the plugin was on, uiscout check --affected origin/main walks only the screens built from changed files, plus the screens one step before them. When a changed file isn't tied to any screen (a store, a hook, a config), it runs everything and says why. Measured: a one-file change walked 5 of 10 screens in 25 s instead of 42 s and found the same errors.

GUIDE · 09

Rules and intent files

Any *.rules.ts file in the app. Each export is a rule, checked on every path walked.

import { always, eventually, state, when } from 'uiscout/rules'

export const emptyCartDisablesOrder = always(
  when(() => state.read('cart.count') === 0)
    .then(() => state.element('cart.order').disabled),
)

export const errorToastClears = always(
  when(() => state.element('cart.toast').visible)
    .then(eventually(() => !state.element('cart.toast').visible).within(5, 'seconds')),
)

export const guestCannotCheckout = always(
  when(() => state.context.is('guest')).then(() => !state.node.is('/checkout')),
)

state reads the context, the screen (state.node.is('/products*')), any element by data-testid or data-scout-id (visible, disabled, name), and values the app exposes when the runner is present:

const hook = (window as { __uiscout?: { read?: () => Record<string, unknown> } }).__uiscout
if (hook) hook.read = () => ({ 'cart.count': cart.items.length })

Time is the app's clock, fast-forwards included, so a five-second deadline costs nothing. A violation is an error that carries the steps from the entry to the state where it broke.

Intent files

Plain sentences in *.intent.md, each linked to a rule. Product people write the lines, developers link them, both are reviewed in the pull request.

- An empty cart disables "Place order".   <!-- rule: emptyCartDisablesOrder -->
- Checkout needs a login.                 <!-- rule: pending -->
Intent coverage 2 of 5 lines
  ✗ failing   cart.intent.md:3  An empty cart disables "Place order".
  ✓ linked    cart.intent.md:4  The error toast goes away by itself.
  · pending   cart.intent.md:6  Checkout needs a login.
GUIDE · 10

Fuzzing

check walks each control once. fuzz takes seeded random walks in odd orders, checks rules and errors after every step, and shrinks each failure to the shortest sequence that still fails. Same seed, same walk.

uiscout fuzz --url http://localhost:5173/ --seed 7 --runs 10 --length 25

uiscout fuzz (seed 7): 1 failure
  rule savedToastClears
  seed 7, shrunk from 6 to 1 step:
    1. /cart.html.button:save-draft@main

Run it nightly rather than on every pull request. It pays off once you have rules; without them it only catches crashes and network errors.

GUIDE · 11

Widget adapters

Calendar grids, gantts, boards and canvas editors are driven by drags and judged by their data. An adapter describes one: real gestures, state read from a debug hook, and invariants checked after every action of a seeded random sequence.

import type { WidgetAdapter } from 'uiscout/adapter'

export default {
  id: 'planning.Gantt',
  harness: '/planning',
  read: (page) => page.evaluate(() => window.__uiscout.gantt.getState()),
  actions: {
    async move(page, { id, minutes }) { /* press, move in steps, release */ },
  },
  generate: (state, random) =>
    state.tasks.map((t) => ({ action: 'move', args: { id: t.id, minutes: (Math.floor(random() * 9) - 4) * 30 } })),
  invariants: [
    (_, next) => next.tasks.every((t) => t.end > t.start) || 'a task ends before it starts',
  ],
} satisfies WidgetAdapter<State, Actions>
uiscout adapters --url http://localhost:5173/ --seed 11 --runs 6 --length 12

calendar.TimeGrid: 1 failure
  moving Lunch changed its duration: 60 → 45 min
  seed 12, shrunk from 7 to 1 action:
    1. move {"id":"3","minutes":15}

The runner creates window.__uiscout before the app loads, so publish the hook only when it exists and production stays untouched. Compare prev with next: "everything else stayed the same" catches the most bugs.

GUIDE · 12

MCP server for coding agents

uiscout mcp serves the project to Claude Code, Cursor or Copilot over stdio. It has no model and needs no API key.

claude mcp add uiscout -- pnpm exec uiscout mcp
ToolDoes
get_graph · get_nodeScreens, actions, API calls, findings
plan_pathThe shortest observed sequence of actions to a screen
get_failures · get_uncovered · get_intentFindings, controls not walked (ranked by traffic when usage exists), intent coverage
run_edgeWalks one control in a real browser and reports where it led
propose_edge · verify_proposalA hypothesis, verified only if the runner observes it
propose_ruleA draft rule; never active until a developer adds it in a pull request

Proposals are quarantined in uiscout/proposals.json, so a wrong guess costs one browser run. Browser tools go only to the url in the config; an agent can't choose the URL.

GUIDE · 13

Production usage overlay

A test map says what uiscout walked. Real traffic says what matters. Ship the plugin's IDs to production (uiscoutIds({ sources: false }), no file paths), then count actions:

import { trackUsage } from 'uiscout/track'

trackUsage({
  send: (batch) => navigator.sendBeacon('/api/uiscout-usage', JSON.stringify(batch)),
  sample: 0.1,
})

Only the route (data IDs collapsed), the control's ID, the kind of action and a count leave the page. No text, typed values, users or sessions. Then import the exports:

uiscout usage import usage-2026-10.ndjson

Usage (uiscout/usage.json: 1,067 actions on tracked controls)
  Usage-weighted coverage 90% (960 of 1,067 actions are on controls the run walked)
  Untested, by traffic
    95  /calendar  calendar.Event.delete  — destructive: walk it with --mode replay
    12  /reports   reports.Page.export    — screen not reached by the walk
  Unused (no use in the period, on screens people visit)
    /settings  settings.Data.importJson  (2,200 views)

Imports accept only safe route and ID characters, so forged batches can't inject markup into pull request comments.

REFERENCE

Safety and sensitive data

uiscout really clicks. Know what it won't do, and what risk is left.

NeverHow
Click something destructiveDelete, remove, clear, reset, log out, pay, send and similar names (English and Vietnamese) are skipped in live and record
Submit through a destructive button with EnterThose forms are typed into, never submitted
Click the wrong control when finding one againSafety is checked again on the element actually found
Follow other sites or open tabsRecorded as external: edges; new tabs closed

Safety comes from names. An unlabelled trash icon may not be recognised: give icon buttons an aria-label, and never run live against production. Recordings are redacted (emails, tokens, JWTs, and whole values under sensitive keys), but pixels in screenshots can't be. Block paid services: "block": ["**/api/ai/**", "https://api.stripe.com/**"].
